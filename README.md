# ACD Zone

اسکلت اولیه‌ی پروژه‌ی جنگو برای ACD Zone — فروش کارت‌های شارژ (ACDPay) و بلیط بالن‌سواری (ACDBallons)، همراه با بلاگ دوبخشی (ACDNews/ACDNotes) و پیگیری سفارش (محصولات من). این مرحله فقط «نصب و راه‌اندازی اولیه» است؛ مدل‌های اصلی (محصولات، پست‌ها، مراحل سفارش، کشورها) طبق توافق در مراحل بعدی و همراه با هم پیاده‌سازی می‌شوند.

## چه چیزی همین الان آماده است

- پروژه‌ی جنگو با ساختار اپ‌ها: `accounts`، `core`، `shop` (ACDPay/ACDBallons/محصولات من)، `blog` (ACDNews/ACDNotes)
- مدل کاربر اختصاصی (`accounts.User`) — از همون اول، تا تغییرش بعداً نیاز به migration دردسرساز نداشته باشه
- دوزبانگی کامل رابط کاربری: فارسی (پیش‌فرض، بدون پیشوند در URL) و انگلیسی (زیر `/en/`)، با راست‌چین/چپ‌چین خودکار
- `django-modeltranslation` نصب و تنظیم شده برای محتوای دوزبانه‌ی مدل‌ها (وقتی مدل‌های واقعی اضافه بشن)
- پنل ادمین سفارشی و دوزبانه با `django-unfold`
- قالب پایه + هدر چسبان (لوگو، لینک داشبورد، سوییچ زبان، درآپ‌داون کشورها به‌صورت جایگاه آماده، ورود/عضویت یا پروفایل) و فوتر (تماس با ما، قوانین، تلگرام، واتساپ)
- صفحه‌ی Home، صفحه‌ی داشبورد، صفحات ACDPay/ACDBallons (با تگ‌های اطمینان + دو محصول نمایشی + بخش ویدیو)، ACDNews (با چهار دسته) و ACDNotes، و محصولات من — همه به صورت اسکلت/نمایشی و آماده برای وصل‌شدن به مدل‌های واقعی
- پالت رنگی (نسخه‌ی دوم، بر اساس تحقیق در مورد پالت‌های لوکس/سفر/فین‌تک — در `static/css/style.css`):
  - زمرد تیره `#0b4f3c` (۳۰٪ — هویت برند: هدر، فوتر، تیترها) — سبز نماد رشد/ثروت/اعتماد
  - طلایی عتیقه `#c6a15b` (۱۰٪ — دکمه‌های خرید/CTA) — لوکس، و برخلاف قرمز حس «خطا» نمی‌ده روی صفحه‌ی پرداخت
  - کرم/پوست‌فیلی `#f8f3e9` (۶۰٪ — پس‌زمینه‌ی غالب) — لوکس آرام، به‌جای سفید خام
  - قرمز آجری (ترکوتا) `#b3452c` — فقط جای کوچیک و حساب‌شده (خط زیر تیترها) نه دکمه، چون توی UI پرداخت قرمز معمولاً یعنی خطا/هشدار
  - فیروزه‌ای تیره `#146b6b` — فقط روی تگ‌های اطمینان ACDPay/ACDBallons، حس سفر/آرامش
  - منبع تصمیم: چند سرچ درباره‌ی پالت‌های لوکس، سفر/گردشگری، روانشناسی رنگ فین‌تک، و ترکیب سبز+قرمز در برندینگ
- زبان بصری مدرن (بر اساس تحقیق روندهای طراحی وب ۲۰۲۶ — همون پالت رنگی، فقط جنس اجراش عوض شده):
  - هدر شیشه‌ای (glassmorphism) با بلور پس‌زمینه که هنگام اسکرول تیره‌تر می‌شود (`static/js/main.js`)
  - دکمه‌های کپسولی (pill) با گرادینت و بالا‌رفتن هنگام هاور، سایه‌های نرم چندلایه به‌جای بوردر تخت
  - بلاب‌های گرادینتی محو («اورورا») پشت هیرو و بخش‌ها؛ آیکون‌های دایره‌ای گرادینتی (`.acd-icon-chip`) به‌جای آیکون خام
  - کارت‌های داشبورد/محصولات به‌صورت بنتو-گرید نامتقارن با اثر بلندشدن هنگام هاور (`.acd-tile`)
  - انیمیشن ظاهرشدن هنگام اسکرول (`.acd-reveal` + IntersectionObserver)، با احترام به `prefers-reduced-motion`
  - فرم‌های ورود/عضویت اصلاح شدند: `BootstrapStyledFormMixin` در `apps/accounts/forms.py` کلاس‌های Bootstrap را خودکار به ویجت‌ها اضافه می‌کند (قبلاً این فرم‌ها کاملاً بدون استایل رندر می‌شدند — دلیل اصلی حس «HTML خام»)
- دیتابیس: SQLite برای الان؛ با تغییر یک خط در `.env` بدون تغییر کد می‌شه رفت روی PostgreSQL

## پیش‌نیازها

- **Python 3.12 یا بالاتر** (django-unfold به این نسخه نیاز داره)
- Git (اختیاری ولی توصیه می‌شود)

## نصب روی ویندوز

```powershell
cd مسیر\پوشه\ACDZone

python -m venv venv
venv\Scripts\activate

pip install -r requirements.txt

copy .env.example .env
```

یک SECRET_KEY تصادفی بساز و توی `.env` جای `SECRET_KEY=` بذار:

```powershell
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

حالا دیتابیس رو بساز و یک ادمین بساز:

```powershell
python manage.py makemigrations
python manage.py migrate
python manage.py createsuperuser
```

و در نهایت اجرا کن:

```powershell
python manage.py runserver
```

سایت: http://127.0.0.1:8000/
پنل ادمین: http://127.0.0.1:8000/admin/

## ترجمه‌ی متن‌های ثابت (نه محتوای دیتابیس)

روش استاندارد جنگو (`{% trans %}` + `makemessages`/`compilemessages`) نیاز به نصب ابزار `gettext` داره که روی ویندوز پیش‌فرض نیست. به‌جای معطل‌شدن روی این نصب، فعلاً از یک مکانیزم جایگزین و ساده‌تر استفاده می‌کنیم:

- `apps/core/translations.py` — دیکشنری کامل فارسی→انگلیسی + تابع `translate()`
- `apps/core/templatetags/acd_i18n.py` — تگ `{% t "متن فارسی" %}` که به‌جای `{% trans %}` توی همه‌ی قالب‌ها استفاده می‌شه (هم با متن مستقیم کار می‌کنه، هم با متغیر مثل `{% t product.title %}`)

هر متن فارسی جدیدی که توی قالب‌ها یا کدهای پایتون اضافه می‌کنی، اگه باید انگلیسی هم داشته باشه، کافیه با `{% t "..." %}` (یا در پایتون با `translate(...)`) بذاریش و ترجمه‌ش رو به دیکشنری `TRANSLATIONS` در `apps/core/translations.py` اضافه کنی — نیازی به نصب gettext یا اجرای هیچ دستوری نیست.

وقتی بعداً gettext نصب شد، می‌شه کامل برگشت به `{% trans %}` استاندارد جنگو (این ماژول دیگه لازم نمی‌شه)، ولی فعلاً همین روش انگلیسیِ کل سایت رو به‌طور کامل و واقعی نشون می‌ده.

## ویدیوی معرفی Home

بخش معرفی سایت توی صفحه‌ی اصلی طوری آماده شده که به محض قرار گرفتن فایل‌های زیر در همین مسیرها، خودش نمایششون می‌ده (بدون نیاز به تغییر کد):

- `static/video/intro.mp4` — خود ویدیو
- `static/video/intro-fa.vtt` — زیرنویس فارسی (اختیاری؛ اگر نباشه فقط ویدیو بدون زیرنویس پخش می‌شه)

توی این نشست دسترسی به اجرای کد (سندباکس لینوکس) نداشتم، برای همین نتونستم خود فایل ویدیو رو تماشا/ترجمه کنم یا فایلش رو از پوشه‌ی آپلودها به این مسیر کپی کنم — این دو کار رو باید یا دستی انجام بدی، یا وقتی سندباکس برگرده کمک کنم:

1. فایل ویدیو رو خودت توی `static/video/intro.mp4` کپی کن.
2. اگه متن گفتاری ویدیو (یا فایل زیرنویس انگلیسی/هر زبونی که هست) رو برام بفرستی، ترجمه‌ش می‌کنم و فایل `intro-fa.vtt` رو با همون زمان‌بندی می‌سازم.

## واردات خودکار روزانه‌ی ACDNews (فارس، ایسنا، مهر، ایرنا، تسنیم، باشگاه خبرنگاران جوان)

دستور مدیریتی `apps/blog/management/commands/fetch_news.py` هر روز که اجرا بشه، از هر کدوم از این ۶ خبرگزاری حداکثر ۲ خبر تازه برمی‌داره، منبع/لینک اصلی رو روش تگ می‌زنه، و خودش تشخیص می‌ده که خبر جزو کدوم دسته (ورزشی/اقتصادی/سیاسی/اجتماعی) هست — همه‌چیز خودکار، بدون نیاز به نوشتن دستی. خبرهایی که قبلاً اضافه شدن (بر اساس لینک اصلی‌شون) دوباره اضافه نمی‌شن، پس اجرای تکراری یا جاافتادن یک روز مشکلی ایجاد نمی‌کنه.

اجرای دستی (برای تست):

```powershell
python manage.py fetch_news
```

برای این‌که واقعاً هر روز خودش اجرا بشه، باید روی سروری که سایت رواش دیپلوی می‌شه (نه روی ویندوز خودت) یک کرون‌جاب اضافه کنی. مثلاً هر روز ساعت ۸ صبح:

```
0 8 * * * cd /path/to/ACDZone && /path/to/venv/bin/python manage.py fetch_news >> /var/log/acdzone_fetch_news.log 2>&1
```

نکته: آدرس RSS فارس و مهر بر اساس الگوی استاندارد rss خودشون گذاشته شده و مستقیم تایید نشده (بقیه‌ی ۴ تا مستقیم چک شدن)؛ اگر یک روز دیدی از این دوتا هیچ خبری اضافه نشد، اول همون آدرس رو (بالای فایل `fetch_news.py`، دیکشنری `SOURCES`) دستی توی مرورگر باز کن و اگه عوض شده بود همون‌جا اصلاحش کن.

## بات تلگرام پشتیبانی (گفتگوی زنده سایت ↔ گروه تلگرام)

وقتی یک مشتری توی ویجت چت شناور سایت پیام می‌ده، همون لحظه یک کپی از پیامش به یک گروه تلگرامی پشتیبانی (که هرچند نفر از تیم می‌تونن توش عضو باشن) فرستاده می‌شه. هر کدوم از اعضای گروه می‌تونن روی همون پیام تلگرام «Reply» بزنن و جواب رو مستقیم توی تلگرام تایپ کنن — جوابشون خودکار به همون گفتگوی مشتری توی سایت اضافه می‌شه، دقیقاً مثل این‌که از پنل ادمین جواب داده باشن.

نکته‌ی مهم: باید حتماً با «Reply» روی همون پیام جواب بدید (نه یک پیام معمولی جدید توی گروه) — چون فقط از همین راه بات می‌فهمه جواب مال کدوم مشتریه.

### راه‌اندازی (یک‌بار)

۱. توی تلگرام به [@BotFather](https://t.me/BotFather) پیام بدید و با دستور `/newbot` یک بات جدید بسازید. یک توکن می‌ده شبیه `123456789:AAExxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx` — همینو بذارید جلوی `TELEGRAM_BOT_TOKEN` توی فایل `.env`.

۲. یک گروه تلگرامی بسازید (یا از یک گروه موجود استفاده کنید) و بات رو به عنوان عضو/ادمین گروه اضافه کنید.

۳. برای پیدا کردن `chat_id` گروه: یک پیام هرچی توی گروه بفرستید، بعد این آدرس رو توی مرورگر باز کنید (به‌جای `<TOKEN>` توکن واقعی بات رو بذارید):

   ```
   https://api.telegram.org/bot<TOKEN>/getUpdates
   ```

   توی جواب JSON، دنبال `"chat":{"id":-1001234567890, ...}` بگردید — همون عدد (معمولاً منفی، برای گروه‌ها) رو بذارید جلوی `TELEGRAM_SUPPORT_CHAT_ID` توی `.env`.

۴. `python manage.py migrate` رو دوباره اجرا کنید (برای فیلد/جدول جدید تلگرام).

### اجرای روزانه/دائمی

طرف «مشتری → تلگرام» نیاز به هیچ اجرای جدا نداره — همون لحظه که مشتری پیام می‌ده، خودش فرستاده می‌شه.

طرف «تلگرام → سایت» (جواب‌های تایپ‌شده توسط شما توی تلگرام) با یک دستور جدا خونده می‌شه، به دو شکل:

**همین الان، روی سیستم خودتون (برای تست/استفاده‌ی فعلی):** این دستور رو یک‌بار توی یک ترمینال جدا اجرا کنید و همون‌جا بازش بذارید — خودش هر ۵ ثانیه یک‌بار چک می‌کنه و تا وقتی باز باشه، جواب‌های تلگرام خودکار میان توی سایت. با `Ctrl+C` متوقفش کنید.

```powershell
python manage.py poll_telegram
```

**روی سرور نهایی (وقتی سایت دیپلوی شد):** به‌جای باز نگه‌داشتن یک ترمینال، بهتره با کرون هر یک دقیقه یک‌بار صداش بزنید (با `--once` که فقط یک‌بار چک کنه و خارج بشه):

```
* * * * * cd /path/to/ACDZone && /path/to/venv/bin/python manage.py poll_telegram --once >> /var/log/acdzone_poll_telegram.log 2>&1
```

اگه `TELEGRAM_BOT_TOKEN`/`TELEGRAM_SUPPORT_CHAT_ID` رو خالی بذارید، این قابلیت کاملاً غیرفعال می‌مونه و ویجت چت خود سایت بدون هیچ مشکلی به کار خودش ادامه می‌ده.

**روش سوم، با داکر:** به‌جای اجرای جدای `poll_telegram` توی یک ترمینال دیگه، `docker compose up` همه‌چیز رو با هم بالا می‌آره — پایین رو ببینید.

## اجرا با داکر

فایل‌های `Dockerfile`، `docker-compose.yml` و `docker-entrypoint.sh` توی ریشه‌ی پروژه هستن. با هر بار `docker compose up`، همین سه تا کار به همین ترتیب خودکار انجام می‌شن:

۱. `python manage.py migrate` (اعمال مایگریشن‌ها)
۲. `python manage.py poll_telegram` در پس‌زمینه (اگه `TELEGRAM_BOT_TOKEN` خالی باشه، خودش بی‌خطر هیچ کاری نمی‌کنه)
۳. `python manage.py runserver 0.0.0.0:8000` در جلوی برنامه (همونی که `docker logs`/ترمینال نشون می‌ده)

```powershell
# اولین بار (یا بعد از تغییر requirements.txt):
docker compose up --build

# دفعات بعدی:
docker compose up
```

سایت روی `http://localhost:8000` بالا میاد. کد و `db.sqlite3` و `media/` از روی سیستم خودتون mount می‌شن (`docker-compose.yml`)، پس تغییرات و داده‌ها بعد از هر بار rebuild از بین نمی‌رن. اگه فایل `.env` دارید (از `.env.example` کپی کرده باشید)، همون‌جوری که هست خونده می‌شه — بدون `.env`، مقادیر پیش‌فرض `settings.py` استفاده می‌شن.

## ساختار پروژه

```
ACDZone/
├── manage.py
├── acdzone/            # تنظیمات پروژه (settings.py, urls.py, ...)
├── apps/
│   ├── accounts/       # کاربر، ورود/عضویت/پروفایل
│   ├── core/           # صفحه‌ی اصلی، داشبورد، تنظیمات سراسری سایت
│   ├── shop/           # ACDPay + ACDBallons + محصولات من
│   └── blog/           # ACDNews + ACDNotes
├── templates/          # base.html + partials/ + قالب هر اپ
├── static/             # css/js/img
├── locale/             # فایل‌های ترجمه (بعداً)
└── media/              # آپلودها (بعداً)
```

## مرحله‌ی بعدی (طبق همون ترتیبی که گفتیم جلو می‌ریم)

- مدل `Country` + صفحه‌ی هر کشور و وصل‌کردنش به درآپ‌داون هدر
- مدل‌های `Category` / `Product` / `Order` در اپ `shop` و منطق «خرید → اضافه‌شدن به محصولات من»
- مراحل سفارش ACDPay — طبق فرآیند واقعی فروش (جزئیات کامل توی کامنت `apps/shop/models.py`):

  | # | کد | فارسی | English |
  |---|----|----|---------|
  | ۱ | `submitted` | ثبت درخواست | Request Submitted |
  | ۲ | `verifying` | در حال استعلام مدارک/مبلغ | Verifying Details |
  | ۳ | `docs_submitted` | مدارک ارسال شد | Documents Submitted |
  | ۴ | `payment_info_sent` | راهنمای پرداخت ارسال شد | Payment Instructions Sent |
  | ۵ | `payment_submitted` | پرداخت ثبت شد | Payment Submitted |
  | ۶ | `payment_confirmed` | پرداخت تایید شد | Payment Confirmed |
  | ۷ | `card_registered` | کارت در بانک ثبت شد | Card Registered |
  | ۸ | `printing` | در حال چاپ کارت | Card Printing |
  | ۹ | `shipped` | ارسال شده به مشتری | Shipped to Customer |
  | ۱۰ (پیشنهادی) | `delivered` | تحویل داده شد | Delivered |

  باید با هم تصمیم بگیریم: مرحله‌ی ۱۰ (تایید دریافت توسط مشتری) اضافه بشه یا نه، و مراحل ۲/۴/۶ (که بیشتر هماهنگی داخلی فروش/مالی‌ان) توی داشبورد مشتری به همین ریزی نشون داده بشن یا به‌صورت یک وضعیت ساده‌ی «در حال پیگیری».

  ACDBallons مراحل جدا و ساده‌تری لازم داره (چاپ/ثبت بانکی نداره) — بعداً جدا مشخصش می‌کنیم.
- مدل `Post` در اپ `blog` با فیلد channel (news/note)، ۴ دسته‌ی ACDNews، تگ‌ها و منبع
- مدل `SiteSettings` برای مدیریت لوگو/ویدیوی معرفی/متن‌های Home از پنل ادمین
- درگاه پرداخت
